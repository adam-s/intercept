# Break-it review — the test suite

Launches an **Opus** general-purpose agent to hunt bugs *in the tests
themselves*, not the production code.

This repo's whole pitch is that a proxy route returns the site's real data. A
suite that lies about that is worse than no suite, and the local hazard is
specific: **every test runs against a fixture or a fake site, never the live
target.** A route can be green forever while the site it proxies changed shape
last week. That is the thing to hunt.

Complementary to [red-team-review](../red-team-review/SKILL.md) (production
code) and [red-team-mutation](../red-team-mutation/SKILL.md) (the dynamic
check); run all three at major change points.

## When to invoke

- User says: "red team the tests", "audit the tests", "find weak tests", "are
  our tests rigorous"
- After adding a large batch of tests
- After a break-it review finds a bug the suite missed — ask "why didn't our
  tests catch this?"
- Before any deploy

## How to invoke

Use the `Agent` tool with:

- `subagent_type: "general-purpose"`
- `model: "opus"`
- `description`: 3–5 words (e.g. `"Break-it review test suite"`)
- `prompt`: the template below

## Prompt template

Fill the bracketed sections with current project state. Do NOT send as-is, and
do NOT name the weakness you already suspect.

```
You are a skeptical code reviewer performing a bug hunt on the TEST SUITE of an
API-interception framework. Your target is the correctness and rigor of the
tests — not the production code. Rank findings CRITICAL / HIGH / MEDIUM / LOW.

## Setup

Repo root: `git rev-parse --show-toplevel`. Read AGENTS.md §"Tests + build" for
what the gate is, and docs/ARCHITECTURE.md for the layout and the commands.
Suites live beside the code they test, plus repo-level pins under
scripts/__tests__. You may run them.

## What's worth hunting — the "how validation lies" checklist

1. **Tautological assertions.** For each test, ask: "if the production code
   were replaced with a no-op, `return []`, or `return input`, would this test
   fail?" If not, it is vacuous. Length-only and existence-only assertions
   where the content is what matters belong here.
2. **Fixture lies — the local hazard.** Recorded responses and the fake test
   sites both freeze a shape. Which tests would still pass if the real site
   changed its field names, nested its payload one level deeper, started
   paginating, or began returning a bot-wall page? Where is a fixture asserting
   only against itself?
3. **Silent skips.** A test that early-returns when a service is absent, a
   browser won't start, or an env var is missing — and reports green. Find
   every guard that turns "could not run" into "passed".
4. **Boundary bypasses.** Tests that exercise the happy path of a function
   whose contract is about the edge: empty result, single page, last page,
   expired session, concurrent access, a total that disagrees with the count.
5. **Stub/fake divergence.** Where the fake site, a stubbed browser, or a
   mocked fetch has different semantics from the real thing — header casing,
   redirect handling, cookie scoping, stream vs buffered body, error shape. A
   test passing against the fake proves nothing where the fake diverges.
6. **Circular fixtures.** A test whose input was generated by the same code
   under test, or a snapshot regenerated whenever it fails.
7. **Coverage gaps.** Production branches no test exercises — error paths,
   cleanup on failure, retry exhaustion, cancellation, malformed input.
8. **Shared-state leakage.** Module-level registries and caches that persist
   between tests; port collisions between suites; profile or fixture
   directories not reset between cases.

## Output

300–600 words. Severity-grouped. For each finding:
- file:line reference
- one-line description of why the test is weak
- concrete trigger: "an implementation that does X would still pass"

No fixes — diagnose only. "No CRITICAL issues found" is valuable signal; say so
explicitly.
```

## Scripts and assets

None. Coverage helpers, if ever needed, live in this folder.

## Cleanup discipline

Same rules as [red-team-review](../red-team-review/SKILL.md): the agent is
read-only, writes no repo files, responds inline, and a final `git status` check
runs before returning control.

Confirmed gaps become tests (preferred), or an accepted-with-reasoning entry at
the code site per the Deferred findings rule in AGENTS.md. Never silent
knowledge.
